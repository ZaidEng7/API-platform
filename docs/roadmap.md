## Phase 4 — Legacy Integration (guide: 10–14 weeks, then continuous)

**Branch:** `phase-4/legacy-integration` (or one branch per adapter once underway)

- [x] CRM Adapter (`integration/crm-adapter`) — **template**, not a real integration: Phase 1 Assessment (which would've supplied the real legacy system's protocol/auth/rate-limits) was deferred, so there's no real system to adapt yet. Built to prove the pattern instead: `api/` (clean REST, canonical `CrmCustomerResponse`) → `legacy/` (anti-corruption boundary — `LegacyCrmClient` + a deliberately fictional `LegacyCrmCustomerRecord` legacy shape) → a stub backend. Full §9.4 resilience config (`resilience4j-spring-boot4` — not yet in `resilience4j-bom`'s dependency management, upstream gap resilience4j/resilience4j#2427, used with an explicit version instead) wired via `@CircuitBreaker`/`@Retry`/`@Bulkhead` + connect/read timeouts on the RestClient itself; `LegacyCrmClientResilienceTest` proves retry/circuit-breaker/fallback actually work against a real embedded WireMock server, not just that the annotations are present. Two real Boot-4-modularization gotchas found along the way: `spring-boot-starter-aop` no longer exists (renamed `spring-boot-starter-aspectj`, which is for full weaving we don't need) — resilience4j's `@Aspect`-annotated classes still need `aspectjweaver` directly on the classpath or their autoconfiguration silently no-ops; and WireMock's static DSL (`stubFor`/`get`) defaults to targeting `localhost:8080` unless `configureStaticDsl(true)` is set on the extension. See `integration/crm-adapter/README.md` for what's real vs. fictional and how to replace the template once Phase 1 happens.
- [x] Onboarding Adapter (`integration/onboarding-adapter`) — **template**, same rationale as CRM Adapter, but the write-side counterpart: demonstrates guide §9.3's legacy-write-semantics rule instead of §9.4's full read-side table. `LegacyOnboardingClient.submit()` deliberately has no `@Retry` (never blind-retry a non-idempotent write — a timeout doesn't tell you whether the write already landed); circuit breaker and bulkhead still apply since they protect the caller, not the write itself. Also bidirectional translation this time (canonical → legacy request, including a `yyyyMMdd`-string legacy date quirk, not just legacy → canonical response). Found and fixed a real bug that also applied (latently) to the CRM Adapter: the default `RestClient` HTTP factory (`ClientHttpRequestFactoryBuilder.detect()`) attempts HTTP/2-over-cleartext via the JDK client, which WireMock's embedded Jetty server rejected on the POST-with-body call (`RST_STREAM: Stream cancelled`) — forced HTTP/1.1 via Apache HttpClient5 (`.httpComponents()`) in both adapters, which is also just more realistic for a legacy system of this era. See `integration/onboarding-adapter/README.md`.
- [x] Fund Management Adapter (`integration/fund-mgmt-adapter`) — **template**, same rationale as the other two, the caching counterpart: demonstrates guide §9.1's caching responsibility, which neither prior adapter needed. The fictional legacy system only republishes NAV once daily after market close, so `FundNavProvider`'s `@Cacheable` (Caffeine, TTL from `fund-mgmt.nav-cache-ttl`) isn't an optimization, it's the design that actually matches that freshness constraint (§9.2 requires documenting exactly this). Caching and resilience are deliberately split across two beans (`FundNavProvider` for `@Cacheable`, `LegacyFundMgmtClient` for `@CircuitBreaker`/`@Retry`/`@Bulkhead`) since Spring's proxy-based AOP doesn't intercept same-class self-invocation — `FundNavProviderCachingTest` proves a second call for the same fund never reaches WireMock at all, not just that the annotation is present. Legacy shape uses a scaled-integer NAV (`NAV_VALUE_X10000`) — a genuinely common real-world legacy-financial-system convention for avoiding floating-point rounding, not just a fabricated quirk this time. All three adapters now built the same way once, so this one hit zero new bugs — reused the HTTP/1.1-forcing fix and WireMock test pattern established by the first two. See `integration/fund-mgmt-adapter/README.md`.
- [ ] Contract tests (Pact) for each adapter — none of the three adapters have one yet; `fund-mgmt-adapter` now has a real consumer (Fund Service, Phase 5 item 5), so it's the natural first one to add — not done yet, see that item's notes. CRM/Onboarding still have no real consumer, so a Pact contract for either would still be asserting made-up behavior.
- [x] **Exit criteria (partial):** Fund Service (Phase 5 item 5) is a real consumer of `fund-mgmt-adapter`'s NAV endpoint — the first real consumer of any Phase 4 adapter, though not yet "through the Gateway in production" (local/CI only so far). CRM/Onboarding adapters still have no real consumer.

## Phase 5 — Business Services (guide: 16–24 weeks, overlaps Phase 4)

Build order is dependency-driven — do not reorder without an ADR:

- [ ] 1. Customer Service (Party data — everything depends on this) — in progress: now publishes `customer.party.created` on customer creation via common-messaging's outbox pattern (guide §8.4/§22), the first real producer that plumbing has had (Audit Service has consumed from `domain-events` since Phase 3, but nothing published to it for real until now). Full `EventEnvelope` is stored as the outbox payload (not just raw domain data), closing a gap `DomainEventAuditListener`'s Javadoc flagged — consumers now see the mandatory envelope shape, including a real `occurredAt`, once relayed. Correlation ID is threaded from `CorrelationIdFilter`'s MDC value straight into the envelope, so a request's correlation ID now flows through logs *and* the event it caused. `CustomerEventPublishingIntegrationTest` proves the full outbox→relay→RabbitMQ path against a real (Testcontainers) broker — not just that the annotations/beans exist. §8.3's "conflict!" cell (interim SoR = Onboarding + CRM) is unaffected by this — it's about legacy reconciliation, a Phase 1/6 concern, not the shape of this new service. Party API surface has since grown beyond the walking-skeleton create/get pair: `Customer` now carries `phone`/`dateOfBirth`/`partyType` (`INDIVIDUAL`/`ORGANIZATION`, defaults to `INDIVIDUAL`), `PUT /api/v1/customers/{id}` updates the mutable profile fields (email and partyType stay immutable there — identity fields, not profile edits) and publishes a matching `customer.party.updated` event, and `GET /api/v1/customers?query=` adds paginated fullName/email search (mirrors Audit Service's own list-endpoint pattern). Still to do before this line item is done: a real consumer of either `customer.party.*` event, and auth (this service wasn't part of Phase 3's identity wiring the way Audit Service was).
- [ ] 2. KYC Service — in progress: new `services/kyc-service` module, target SoR for "KYC status" (§8.3). `KycCheck` lifecycle is PENDING → APPROVED/REJECTED (once only — deciding an already-decided check is `409 KYC-4090`), driven entirely by human Compliance review via the API — deliberately **no** decisioning logic (rules engine, sanctions screening, fraud scoring), since those compliance business rules don't exist yet (§3.1 sign-off still pending, same blocker noted for Phase 2). Publishes `customer.kyc.requested` on request and, on decision, `customer.kyc.approved`/`customer.kyc.rejected` — the exact event names the guide's own §22 naming example uses. Unlike Customer Service, this one has real authorization from day one: `common-security`'s JWT/`@PreAuthorize` wiring (same pattern as Audit Service), with the decision endpoint gated to the `compliance` realm role alone, matching that role's own description in `platform/identity/realm-export.json` ("Compliance/AML/KYC review and sign-off"). `KycEventPublishingIntegrationTest` proves all three event types really reach RabbitMQ end to end. Gateway now routes `/api/v1/kyc-checks/**`; `deployment/helm/values/kyc-service.yaml` and the CI container-scan/k8s-smoke-test matrices were extended to match. Still to do: a real consumer of any `customer.kyc.*` event (Customer Service's own KYC-status read model, per §8.3's "Read copies allowed in" column, is the natural first one).
- [ ] 3. AML Service — in progress: new `services/aml-service` module, "compliance gate for money movement" alongside KYC Service, screening lifecycle IN_PROGRESS → COMPLETED(CLEAR/HIT)/FAILED. Async by design per the guide's own §10.3 example verbatim: `POST /api/v1/aml/screenings` returns `202 Accepted` + `Location` header (not `201` — the first synchronous-vs-async distinction actually exercised in this codebase), `GET .../{id}` polls status. No real watchlist/sanctions vendor integration (same rationale as KYC's no-decisioning-logic stance) — a human Compliance reviewer supplies CLEAR/HIT via `POST .../{id}/result` (gated to the `compliance` role, once only — `409 AML-4090` on retry), and Operations can mark a screening technically `FAILED` via `POST .../{id}/fail` (gated to `operations`, same once-only rule) — a system failure distinct from a compliance HIT. Publishes `customer.aml.requested`/`cleared`/`flagged`/`failed` via the outbox; `AmlEventPublishingIntegrationTest` proves all four reach RabbitMQ end to end. Gateway now routes `/api/v1/aml/**`; Helm values, CI container-scan/k8s-smoke-test matrices, and the Prometheus scrape config were extended to match. Still to do: a real consumer of any `customer.aml.*` event, and the eventual real watchlist vendor adapter (would plug in by calling `.../result`/`.../fail` itself, without changing this service's public contract).
- [ ] 4. Document Service (KYC needs it) — in progress: new `services/document-service` module, target SoR for "Documents" (§8.3: read copies "— (references only)", so no read-model sync concern here unlike Customer/KYC/AML). Metadata-only by deliberate scope decision — stores an opaque `storageReference` pointer, never actual file bytes, so the guide's "never log document contents" rule (§14) is structural rather than policy. Lifecycle UPLOADED → VERIFIED/REJECTED (once only, `409 DOC-4090` on a second review), `compliance` role gates both `.../verify` and `.../reject` (no `operations`-only failure path here, unlike AML — document review doesn't have a distinct "system failure" concept). Publishes `customer.document.uploaded`/`verified`/`rejected` via the outbox (the uploaded event deliberately omits `storageReference` — no reason for every consumer to receive the storage pointer); `DocumentEventPublishingIntegrationTest` proves all three reach RabbitMQ end to end. Gateway now routes `/api/v1/documents/**`; Helm values, CI matrices, and Prometheus scrape config extended to match. Still to do: a real consumer (KYC Service is the natural first one — this is literally why the guide lists this item), and eventual real DMS/object-store integration behind `storageReference`.
- [ ] 5. Fund Service — in progress: new `services/fund-service` module, target SoR for "Fund / NAV" (§8.3). **First real consumer of a Phase 4 legacy-integration adapter**: `FundNavClient` calls `fund-mgmt-adapter`'s `GET /api/v1/funds/{fundCode}/nav` over HTTP and stores the result as a `NavSnapshot` — that adapter had no real consumer since it was built (see Phase 4's exit-criteria note above). Fund existence itself isn't sourced from the adapter (it only exposes NAV lookup by an already-known code), so fund registration is staff-driven like the other Phase 5 services. `POST .../nav/refresh` is manual/on-demand, not scheduled — deliberately, to avoid a timing-flaky test for a mechanism nothing yet depends on (a real deployment would likely schedule it per the adapter's refresh SLA). The adapter call skips the full §9.4 resilience table (retry/circuit-breaker/bulkhead) the adapters apply to *legacy* calls — connect/read timeouts only, since the callee is one of our own services, not a legacy system; see `FundNavClientConfig`'s Javadoc for the reasoning. `FundNavRefreshIntegrationTest` proves the adapter call for real (WireMock standing in for `fund-mgmt-adapter`, including the 404-before-ever-calling-the-adapter and 503-on-adapter-down cases); publishes `fund.definition.registered`/`fund.nav.updated` via the outbox, proven end to end by `FundEventPublishingIntegrationTest`. Roles use `portfolio-manager` for the first time (paired with `operations`, same pattern as the other services). Gateway now routes `/api/v1/funds/**`; Helm values, CI matrices, and Prometheus scrape config extended to match. Still to do: a real consumer of either `fund.*` event (Portfolio/Reporting Services, per §8.3's "Read copies allowed in" column), and a Pact contract between this service and `fund-mgmt-adapter` now that a real consumer relationship exists.
- [ ] 6. Portfolio Service — in progress: new `services/portfolio-service` module, target SoR for "Portfolio positions" (§8.3). **First real enforcement of guide §12.2's object-level authorization rule** ("an Investor sees *their* portfolio only... every `GET /portfolios/{id}` must verify ownership — the #1 API vulnerability class, BOLA/IDOR") — `common-security`'s `CurrentUser`, whose own Javadoc has cited this exact rule since Phase 3, finally gets used for authorization rather than just decision-attribution (`decidedBy` in KYC/AML). `Portfolio.ownerId` is treated as directly comparable to the JWT `sub` claim, since no Identity-to-Party linkage table exists anywhere in this platform to build a richer mapping from. Staff roles (`operations`/`portfolio-manager`/`auditor`/`compliance`) see any portfolio; an `investor` sees only their own (`403 PORTFOLIO-4030` otherwise) — proven with Spring Security Test's `jwt()` post-processor, not `@WithMockUser` (which can't assert a specific caller identity `CurrentUser.subject()` can read). Also the **second real inter-service consumer chain**: `GET /{id}/valuation` calls Fund Service's NAV endpoint per distinct fund held (Portfolio → Fund Service → `fund-mgmt-adapter` → legacy product) — same connect/read-timeout-only resilience stance as that first chain, and an all-or-nothing valuation (no partial results) if any fund's NAV can't be obtained. Positions/portfolio-opening are staff-driven, like every other Phase 5 write path. Publishes `portfolio.account.opened`/`portfolio.position.recorded` via the outbox; `PortfolioEventPublishingIntegrationTest` and `PortfolioValuationIntegrationTest` (WireMock standing in for Fund Service) prove both end to end. Gateway now routes `/api/v1/portfolios/**`; Helm values, CI matrices, and Prometheus scrape config extended to match. Still to do: a real consumer of either `portfolio.*` event (Reporting Service/Client Portal, per §8.3), FX conversion in valuation, investor self-service, and a Pact contract with Fund Service.
- [ ] 7. Investment Service (subscription/redemption sagas, §8.4) — in progress: new `services/investment-service` module. Only **subscription** built, not redemption (a near-mirror-image flow, natural follow-up, not built speculatively). Implements the guide's own named saga steps ("validate customer → KYC/AML check → reserve units → collect payment → confirm → notify") without distributed 2PC: steps 1-3 run synchronously inside the initiating `POST` (all three downstream services are our own fast REST APIs, not a legacy batch process, so no need to persist intermediate state between them); only "await payment" — the one genuinely long-running step — gets durable state, a timeout, and a dead-letter path. "Collect payment" has no real callee (Payment Service is item 8, built *after* this one in the guide's own order) — modeled as a human/finance-ops confirmation (`POST /{id}/confirm-payment`) rather than a fake PSP integration, same "human/future-service supplies the missing piece" pattern as KYC/AML/Document. `POST /{id}/cancel` (the guide's own exact example endpoint) is the compensating action — no separate inventory hold exists to release, so cancelling *is* the full compensation. `POST /api/v1/subscriptions` requires a client-generated `Idempotency-Key` header (guide §12.3) and is replay-safe (a repeated key returns the original subscription, proven by asserting Customer Service is only called once across two identical requests). `SubscriptionTimeoutJob` (reusing `OutboxRelayPublisher`'s own `@Scheduled` mechanism) implements guide §8.4's "every saga has a timeout and a dead-letter path" for real — `SubscriptionTimeoutJobIntegrationTest` shrinks the timeout to prove the job actually runs. Publishes `investment.subscription.reserved`/`failed`/`confirmed`/`cancelled`/`timed-out` — `confirmed` is the exact event name the guide's own §22 example uses. Not fixed here (see the module's README) — worth its own ADR (guide §26) before any secured deployment. Gateway now routes `/api/v1/subscriptions/**`; Helm values, CI matrices, and Prometheus scrape config extended to match.
